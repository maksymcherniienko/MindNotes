### 1. Архітектурне розділення: Клієнт-Сервер замість On-Device AI

* **Рішення:** Винести AI-обробку на окремий FastAPI бекенд замість виклику Gemini API або локальних LLM безпосередньо з Android-клієнта.
* **Причини:**
  * **Безпека секретів:** Захист `GEMINI_API_KEY` від витоку (ключ зберігається у `.env` на сервері й не потрапляє у декомпільований APK).
  * **Гнучкість промптів і моделей:** Можливість змінювати системні промпти, версії моделей чи перемикати провайдерів без оновлення та перезбирання мобільного додатку.
  * **Продуктивність клієнта:** Економія пам'яті, батареї та трафіку мобільного пристрою.

---

### 2. Вибір технологічного стека

* **Рішення:** **FastAPI + Pydantic (Python)** для бекенду, **Jetpack Compose + Kotlin Coroutines** для мобільного клієнта.
* **Причини:**
  * **FastAPI:** Асинхронність, вбудована строга валідація схеми запитів/відповідей через Pydantic DTOs, автоматична генерація OpenAPI документації, нативна сумісність з офіційним SDK `google-generativeai`.
  * **Jetpack Compose:** Декларативний підхід спрощує реалізацію реактивного керування станами екрана через єдиний `UiState`.
  * **HttpURLConnection замість Retrofit на етапі MVP:** Мінімізація зовнішніх залежностей для швидкого старту та простоти контролю низькорівневих мережевих помилок.

---

### 3. Дворівнева обробка: Gemini AI + Евристичний Fallback

* **Рішення:** Реалізація резервного алгоритму [`local_analyze`](file:///C:/Users/h0nza/AndroidStudioProjects/MindNotes2/backend/main.py#L40) на базі регулярних виразів і ключових слів.
* **Причини:**
  * **Відмовостійкість (Fault Tolerance):** Якщо сторонній AI API недоступний (ліміти квот, мережеві збої або відсутність ключа у середовищі), бекенд не падає з кодом 500, а повертає базово структуровану відповідь.
  * **Локальна розробка:** Можливість тестувати клієнт-серверну взаємодію локально без активного підключення до Gemini API.

### 4. Робота з відносним часом і контекстом у Промпті

* **Рішення:** Динамічна ін'єкція поточного часу сервера (`now_str`) у промпт моделі перед кожним викликом.
* **Причини:**
  * LLM за замовчуванням не знає актуальної дати й не здатна коректно інтерпретувати відносні часові маркери ("завтра о 15:00", "у п'ятницю", "через 2 години").
  * Серверний час слугує єдиною точкою відліку для формування точного абсолютного значення `reminder_datetime` у форматі `YYYY-MM-DD HH:MM`.

### 5. Суворий структурований вихід AI (JSON Mode + Temperature 0.2)

* **Рішення:** Примусове використання `response_mime_type="application/json"` та зниженої температури генерації (`0.2`).
* **Причини:**
  * **Передбачуваність схеми:** Гарантує стабільний JSON без випадкового Markdown-тексту навколо, що критично для автоматичного мапінгу у Pydantic/Kotlin моделі.
  * **Детермінізм:** Низька температура мінімізує галюцинації при виборі категорій із фіксованого списку та визначенні дедлайнів.

---

### 6. Реактивна модель UI через єдиний `UiState`

* **Рішення:** Використання закритого класу `sealed class UiState` із 4 станами: `Idle`, `Loading`, `Success`, `Error`.
* **Причини:**
  * **Передбачуваність інтерфейсу:** Виключає неконсистентні стани (наприклад, одночасне відображення спинера завантаження та повідомлення про помилку).
  * **UX / Error Recovery:** Можливість показувати людинозрозумілі повідомлення про помилки мережі (`getReadableErrorMessage`) та надавати дію повтору (`Retry`) без втрати введеного тексту.
